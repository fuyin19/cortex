# Registry and agent runtime

A KB root contains canonical Registry 1, a stable zero-byte `.cortex.lock`, direct-child Bundles, and unrelated ordinary entries ignored by discovery. Registered Bundle mutations and record authorization retain the same nonblocking exclusive root lock; standalone Bundles lock `profiles/record-schema.json`.

All three canonical KB skills carry the same complete Cortex 8.0.0 wheel, isolated runner, and Windows convenience launcher: `cortex-kb-ingest`, `cortex-kb-build`, and `cortex-kb-manage`. `CORTEX_PYTHON` must be a lexical absolute ordinary non-reparse file, reached through non-reparse ancestors, that is the same filesystem entry as the running Python 3.11/UCD 14 executable. `ANTI_ENTROPY_CORE_RUNNER` must separately name the explicit absolute anti-entropy Core runner used for envelope inspect/validate/repair/stage completion; Cortex performs no PATH lookup, plugin discovery, runtime import, or local fallback. POSIX invokes `"$CORTEX_PYTHON" -I`; Windows may use `run_cortex.cmd`. No installed global command, ambient-package, network, sibling-skill, or update fallback exists. Human stdout/stderr is UTF-8 while compact JSON Results retain ASCII escaping.

The independent `cortex-collaborative-workspace` skill carries `cortex-collaborative-workspace` 1.1.0 and exposes only prepare, status, and validate for one absolute Collaborative Workspace root. It delegates the outer and inner workspace envelopes plus every prepared KU to the same explicit Core runner. Prepare uses task-owned source snapshots and exact configured file-conversion/markdown-conversion runners, excludes outer `ref/_outdated/` from active projection, preserves retired prepared KUs by generation, and adds no KB/Notes coupling, provider discovery, background execution, deletion, or recovery layer.

`cortex-kb-ingest` owns `record.add`; `cortex-kb-build` owns init/profile/Registry writes; `cortex-kb-manage` owns reads/validation and exact record show/edit/delete. These are skill-contract boundaries: each embedded runtime still exposes the complete closed CLI. Only `cortex-kb-ingest` carries the non-core `batch_record_add.py` helper. It accepts the unchanged exact v1 syntax and the exact v2 source/conversion/both syntax. It validates the whole job before invoking the same interpreter and verified runner sequentially for each `record add`; it has no concurrency, rollback, inference, deletion, or persistent job state.

One build session binds one explicit target and uses full JSON operands. Existing Tag group/tag keys retain exact relative order and membership, new keys append, descriptions may change, and Registry id-to-path keys expand monotonically. Populated Bundles accept complete keyed-monotonic Tag 2 candidates while Layout 5 bytes cannot change. Empty configured Bundles retain their group and strategies and may only preserve/increase the maximum; maximum expansion precedes Tag writes. Empty null-sentinel Bundles write Tags first and then select an existing candidate group. Contraction rejects prewrite. The first failed step ends execution with no later write or rollback and an explicit completed/failed/residual/orphan/core-Result report.
