# Record Bundle architecture

Layout 5 keeps the Layout 4 partition dimension and makes every record a complete minimal knowledge unit. A record root contains Core-governed `AGENTS.md` and `CLAUDE.md` navigation controls, Cortex-private `record.json`, root representations, `assets/`, and `src/`. Cortex delegates all base-envelope inspect/validate/repair/stage-completion decisions to the exact sibling `anti-entropy-core` skill selected by the installed launcher, or an explicit absolute `ANTI_ENTROPY_CORE_RUNNER` override; it retains only record metadata, profile, partition, naming, and explicit-source consistency rules and has no local envelope fallback.

Add derives its partition from metadata. Existing and newly created partitions use bounded sibling staging and no-replace publication. Edit/show/delete authorize the exact `--partition` plus `--record` pair. V2 tree hashing prefixes the UTF-8 partition and unit lengths/bytes before the sorted no-follow manifest. Delete removes the authorized unit leaf-first and removes its now-empty partition; partial failure is reported without recovery artifacts.

Role ownership is deliberately outside the core route surface. Within `$cortex`, `kb.ingest` owns add and batch, `kb.build` owns initialization/configuration/registration, and `kb.manage` owns reads/validation and exact record show/edit/delete. The private KB adapter remains complete. `record add` requires metadata and at least one of source or conversion: source-only creates one root representation, conversion-only completes an owned input bundle, and both require the retained source to match by basename and SHA-256. The ingest helper preserves exact v1 syntax and adds exact v2 source-only, conversion-only, and both forms. It validates the whole job before any runner call, then invokes `record.add` sequentially and collects valid non-ok Results without rollback or persistent state. Only the private KB adapter carries the helper.

Build is a skill-level ordered transaction protocol without rollback or extra durable state. It binds one explicit target; validates complete candidate Tags, Layout, and Registry objects against keyed-monotonic retention; and rejects contraction before writing. Existing Tag keys retain order and membership, new keys append, and descriptions may change. Populated Bundles accept complete keyed-monotonic Tag 2 candidates while Layout 5 stays byte-identical. Empty configured Bundles retain their group/strategies and may preserve/increase the maximum, writing Layout before Tags only for a maximum increase. Empty null-sentinel Bundles always write Tags before selecting an existing candidate group in Layout. Registry is last. The first failure stops later steps and reports the exact residual/orphan state together with the core Result.

The sole repository migration utility is the noninstalled `tools/migrate_layout.py` dispatcher. It preserves deterministic Layout 3 → Layout 4 plan/build and adds deterministic Layout 4 → Layout 5 plan/build. Both edges keep the source read-only, aggregate validation defects before output, publish only a separate absent candidate, protect the Cortex repository, initialized KB root, derived KB repository, and same-volume staging boundary, and expose no product fallback, adoption, or cutover route. The 4 → 5 edge preserves every existing record path and byte while adding only the exact navigation controls and required empty support state.

KB 8.1.1 preflights exact Core 1.2.1 and ABI `anti-entropy-core.runner/v1` through a 30-second isolated JSONL request before business writes. It retains the selected runner throughout one operation. Empty/invalid explicit overrides and missing, nonordinary, or reparse paths fail closed without searching another root. Direct source/library use requires explicit configuration; Notes, help/version, and KB init remain Core-independent.
